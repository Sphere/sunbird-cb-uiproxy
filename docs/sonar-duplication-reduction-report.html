Why the codebase changed, module by module

A plain-English record of every cleanup done so far: what was combined, why it was safe to combine, and what was deliberately left alone. No jargon, nothing skipped.

That's roughly 10,000 fewer duplicated lines out of an original ~12,400 — measured by SonarQube, the tool that scans the code and reports this number.

What "duplication" means here: in several places across the app, the same piece of logic — usually "call this other service, then send the result back, and if something goes wrong, log it and show an error" — had been copy-pasted into many different files or many different sections of the same file, instead of being written once and reused.

What "cleaning it up" means: finding those copies, checking carefully that they really do the same thing, and combining them into one shared piece of code that every copy now calls. Wherever two copies looked the same but actually did something slightly different — a different web address, a different error message, an extra step one of them takes — that difference was kept, not erased. It just became a setting passed into the shared code instead of being baked into a separate copy.

Early rounds — small, safe fixes

Before the big duplication push, a first pass caught small code-quality and security issues one at a time.

change 1randomPasswordGenerator.ts

New-account passwords now use a proper secure random generator

The way new account passwords were generated used a random-number method that, in theory, could be predicted. Swapped it for a cryptographically secure one. The password length and character rules are exactly the same — only how "random" is produced changed.

Real security fix This one wasn't about duplication — it closed an actual weakness.
change 2keycloak-user-creation.ts

Removed a piece of error-handling code that could never run

There was a safety-net block meant to catch errors, but it was written in a way that meant it could never actually catch anything. Removed the dead block and added a proper one that does work.

Why safe The block being removed genuinely never ran, so removing it changes nothing.
changes 3–5navigator.ts, dataAlterer.ts, realTimeProgress.ts

Small readability cleanups with no behavior change

Simplified a nested if/else chain, gave two pieces of logic their own clear names, and modernized two variable declarations. None of these change what the code actually does — they just make it easier to read.

change 6connections.ts, socialv2.ts, userDataMigration.ts (deleted)

Deleted three files that nothing in the app was actually using

Confirmed through multiple checks (commented-out references, file history, exhaustive route lists) that these three files were never reachable by any real request. Deleted them along with their tests.

Bug found in the deleted code One of the deleted files had a real security flaw — it skipped OTP verification before letting someone reset a password. Since the file was already unreachable, this posed no live risk, but it's flagged in case anyone considers bringing that file back.
change 7whitelistApis.ts

Simplified the security permissions list from ~1,900 lines to ~725

This file lists every web address in the app and which permission checks apply to it. 301 of 306 entries used the exact same 3 permission combinations, just copy-pasted repeatedly. Replaced the repeats with 3 reusable presets.

Why safe Ran an automated check proving the final permission rules are identical, address by address, for all 306 entries — not just the ones with tests.
changes 11–12server.ts, various small files

Configuration cleanup and 16 small code-quality fixes

Moved one hardcoded web address into a proper setting (keeping the same address as the fallback), and cleaned up 16 minor issues flagged by the code-quality scanner — mostly dead code and imprecise error handling.

Sign-up and login files

This app has several nearly-identical sign-up flows for different partner organizations (UPSMF, MP-NHM, BNRC, and a few others), plus several sign-up variants for the main app. A lot of duplication lived here, because these were clearly built by copying one flow to create the next.

changes 9, 22, 30upsmfUser.ts, mpNHMUser.ts, bnrcUser.ts

Combined the shared setup and logic across the three partner sign-up files

These three files each independently rebuilt the same database connection setup, the same list of web addresses, and the same form-validation rules. Combined all of that into shared, reusable files. Later, six more pieces of actual sign-up logic (create user, send SMS code, etc.) were also combined into a new shared helper file.

Why safe Every genuine per-organization difference — custom log wording, one organization's longer network timeout, different postal-address text — was kept as an explicit setting, not erased. Each file still gets its own separate database connection, deliberately, since sharing one would have reduced how many connections were available under load.

Combined "create account," "update profile," and "check if user exists" logic

Three sign-up files (plus a login file) had identical copies of these three pieces of logic. Combined them into shared, reusable files.

Why safe One file uses a genuinely different login-timeout setting than the others — that difference was kept separate, not merged away.
change 23emailOrMobileLoginSignIn.ts

Combined two login methods' shared "exchange code for session" step

The same 55-line block that swaps a one-time login code for an actual logged-in session appeared twice in one file, for two different login methods. Combined into one shared piece; each login method still builds its own request beforehand exactly as before.

change 31tnaiAuth.ts, tnnmcAuth.ts, sashaktAuth.ts, maternityFoundationAuth.ts

Combined the shared "exchange login code with our partner Keycloak system" step

Four different partner-login files share one identical middle step: exchanging a login code with the shared authentication system. Combined just that one step into a shared file.

Why safe Deliberately did NOT try to merge the rest of each file's logic — the failure handling, redirect behavior, and response shape genuinely differ between partners, and forcing those together would risk wiring the wrong behavior to the wrong partner.
change 33signupWithAutoLogin.ts, signupWithAutoLoginV2.ts, appSignUpWithAutoLogin.ts

Combined the shared "send and verify OTP code" logic across 3 sign-up files

The one-time-passcode sending and checking logic was duplicated across three sign-up files. Combined it into one shared file.

Real bug found and fixed While combining this, an early draft of the merge accidentally introduced a bug where the app could try to send two responses to the same request — something Express (the web framework) doesn't allow, and would have crashed that request. The existing automated tests caught this immediately, before it ever reached production, and it was fixed the same session. The final, shipped version has no bug.

Error-handling cleanup, file by file

By far the most common type of duplication in this app: the same "call the backend, then either send the result or log an error and send a failure message" pattern, repeated once per web address inside a single file. Across dozens of files, these repeats were combined into one shared piece of code per file (or, where the text was truly identical everywhere, one shared piece of code used by several files).

Both files have many web addresses that all do the same thing: call a backend service with a standard set of headers, then send back whatever it returns. Combined 9 of 9 addresses in one file, and 9 of 12 in the other.

Combined 5 similar "homepage configuration" web addresses into one shared piece of code. And combined two routes that both check a user's login token and then look something up.

What's deliberately left alone, and why

Not everything that looks like duplication can be safely combined. These are the parts of the codebase that were investigated and specifically decided against touching — not overlooked, decided.

The security permissions table (whitelistApis.ts)

This one file used to account for about an eighth of all duplication in the entire codebase on its own. It isn't repeated logic — it's a giant table that decides, for every single web address in the app, exactly which permission checks apply. The only thing repeating is the same-shaped rule appearing next to hundreds of genuinely different, individually important addresses. There's no way to compress this further without risking either silently removing a security check from one address, or silently copying one address's permissions onto a different one by mistake.

The three partner sign-up files (UPSMF, MP-NHM, BNRC)

A large amount of what's safely shareable between these three files has already been combined. What's left is genuinely different for each organization: different job-role lists, different job-title naming, different contact emails, different address formats — and, in a few places, each file already has its own different pre-existing bug. Merging what's left would risk quietly applying one organization's rules to a different one.

The five partner-login files (SSO / single sign-on)

Checked twice, including a final dedicated re-check specifically to make sure nothing safe was being missed. The login credentials themselves were already safely combined earlier. What's genuinely different, file by file, is what happens right after login: each partner sends back a different set of profile fields, and one file does an extra database step none of the others do. No two of the five files even match each other closely enough for a safe partial merge. The existing tests also don't check the exact data being sent closely enough to safely catch a bad merge here — so touching this without much more test-writing first would be genuinely risky, not just theoretically risky.

The role-definitions file (roleActivity.ts)

Similar situation to the permissions table — this isn't code logic, it's fixed reference data (a list of roles and what they mean) that happens to share the same data shape across different roles. There's nothing to "combine" here in a meaningful sense.

Plain-English glossary

A few terms used throughout this document, explained simply.

Duplication / duplicated lines
Code that appears, word-for-word or near-enough, in more than one place. Measured automatically by a tool called SonarQube, which scans the whole codebase and reports what percentage of it is repeated.
Combining / merging
Taking two or more copies of the same logic and replacing them with one shared version that everyone calls, instead of everyone having their own copy.
Threading through as a setting
When two copies are almost identical but not quite — say, they call different web addresses — the shared version is written to accept "which address" as an input, so each caller still gets its own correct behavior.
Route / web address / endpoint
A specific URL path the app responds to, like /getUserProfile. Each one usually has its own small block of code handling it.
Regression test / automated test
A small program that runs the real code and checks the result matches what's expected. If a change accidentally breaks something, a test is supposed to catch it immediately, before anyone else does.
SonarQube / the scanning tool
The automated tool that measures duplication percentage, among other code-quality things. It needs to be running to get a fresh number — the two most recent changes in this report were made and fully tested, but the tool happened to be offline, so their exact effect on the percentage isn't confirmed yet.
Every change described here went through the same process before being accepted: read both copies of the code in full, confirm exactly what's the same and what's genuinely different, combine only the truly-identical parts, keep every real difference as an explicit setting, then re-run the full automated test suite (thousands of tests) two or three times to confirm nothing broke, plus a full production build check. Full technical detail for every change lives in docs/PROD-VERIFICATION.md.
