## Summary

Scanning the QR code on an event or workshop certificate said the certificate could not be verified, even though it was genuine. Verification only understood course certificates. Event certificates now verify too, showing the participant's name, the event name and the event date.

## 🐛 Fixes

- **Event certificate QR verification** — `GET /public/v8/certificate/verify/:id` found the event record in Sunbird RC but discarded it, because it looked for the learner only where course certificates keep it (`recipient.name` or the signed `recipientName`). Event certificates (sent by `rcEvents` through rc-proxy-mapper) are flat records: `name`, `workshop-name`, `date`, `place`, plus any field a schema maps, such as `courseName`. For any entity other than `TrainingCertificate`, the route now reads the participant from `name`, the title from `courseName` / `workshop-name` and the date from `date`, from the record or else the signed credential. Course certificates are read exactly as before (`c8396d9`).

## ⚠️ Deploy notes & risk

- **Code-only change, no settings.** The learner portal `/certs` page already sends the QR's `entity` and shows whatever the route returns, so no portal release is needed.
- **No certificate image for events.** The verify page shows the details but no certificate preview, because the preview comes from the course-certificate download API. Unchanged from before.
- **Staging course certificates still fail** for a separate reason: staging RC has `authentication_enabled: "true"`, so anonymous `TrainingCertificate` reads are redirected to SSO login. That is a staging setting, not part of this release.
- **Never deploy to the old production cluster** (`aastar-prod-eks`, namespace `dev`); this build is for Spark.
- **Risk:** low. Only the public verify view of non-course certificates changes.

## Verification performed

Before the fix, prod answered `{"found":false}` for event certificate `1-adb9c96b-…` (decoded from a generated PDF's QR), while course certificate `1-dafbf8a9-…` returned `found:true`. On staging, Sunbird RC returned both event records (`DynamicEventCertificate`, `Ddd`) with HTTP 200, and ui-proxies logged them as "not found by id or oldId". The new test cases use those records' real shapes.
