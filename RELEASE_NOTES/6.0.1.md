## Summary

Scanning a certificate's QR code on production showed the access-code box instead of the verified certificate, even for a certificate issued the same day. The certificate was in Sunbird RC and signed correctly; the proxy just could not find the learner's name in what RC sent back, so it treated the certificate as unknown. This release reads the name from the signed credential when RC leaves it out, so every certificate verifies.

## 🐛 Fixes

- **Certificate verification on production** — Sunbird RC's read-by-id leaves out nested parts of the record, and not the same part on every environment: staging drops `training`, production drops `recipient`. Without `recipient` the proxy had no learner name, answered `found: false`, and the page fell back to the access code. The learner name now comes from the signed credential (`_osSignedData.credentialSubject.recipientName`) whenever `recipient` is missing, as the course name and date already did in 6.0.0. A record with no name anywhere is still rejected (`ba2a3d5`).

## ⚠️ Deploy notes & risk

- **Code-only change, no settings.** Only the certificate verification route (`GET /apis/public/v8/certificate/verify/:id`) is affected; nothing else in the proxy changes.
- **Never deploy to the old production cluster** (`aastar-prod-eks`, namespace `dev`); same as 6.0.0, this build is for Spark.
- **Why RC drops nested parts is not yet known.** The signed credential is complete either way, which is why the fix reads from it. Worth raising with whoever owns the registry, since other RC readers may hit the same gap.
- **Logging:** the route logs at info level, which production does not print. A failed verification leaves no trace in the logs; check it by calling the route directly (see the checklist).
